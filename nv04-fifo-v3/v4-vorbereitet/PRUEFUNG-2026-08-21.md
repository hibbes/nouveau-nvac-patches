## B) Befunde nach Schwere

### B1 BLOCKER: `nouveau_fence_context_arm()` greift in der falschen Reihenfolge zu

**Befund.** Ein Handschlag dieser Bauart ist das Store-Buffering-Muster:
jede Seite speichert **zuerst** ihre eigene Marke und liest **danach** die
fremde. Die Kill-Seite tut das. `arm()` tut das Gegenteil.

Beleg, `2von4-handschlag.diff:70-73`:

```
+	spin_lock_irqsave(&fctx->lock, flags);
+	killed = atomic_read(&chan->killed);      <- laedt die FREMDE Marke zuerst
+	atomic_set(&fctx->ready, 1);              <- speichert die EIGENE danach
+	spin_unlock_irqrestore(&fctx->lock, flags);
```

gegen `2von4-handschlag.diff:9,20,23`:

```
 	atomic_set(&chan->killed, 1);
+	smp_mb();
+	if (fctx && atomic_read(&fctx->ready))
```

**Selbst nachgerechnet.** Ich habe alle Verschraenkungen unter sequentieller
Konsistenz durchgezaehlt, unter Beibehaltung der Programmordnung je Seite
(`v4-vorbereitet/sc-interleavings.py`):

```
AS WRITTEN (arm: LD killed, ST ready): 6 interleavings, 1 lose the kill
   witness: A0 / K0 / K1 / A1
FIXED (arm: ST ready, LD killed): 6 interleavings, 0 lose the kill
```

Der Zeuge im Klartext: `arm()` liest `killed`==0, `kill()` setzt `killed`=1
und liest `ready`==0, `arm()` setzt `ready`=1. Beide steigen aus. Weil SC
das staerkste Modell ist, das eine Maschine anbieten kann, ist ein dort
erreichbarer Ausgang auf jeder Maschine erreichbar. Daraus folgt: das
`smp_mb()` in `kill()` ist nicht falsch platziert, es ist gegen diesen
Ausgang wirkungslos, und **keine** Schranke auf irgendeiner Seite kann ihn
verbieten.

Die Sperre hilft nicht. In der verlierenden Verschraenkung kehrt `kill()`
bei `2von4-handschlag.diff:23` zurueck, ohne `fctx->lock` je anzufassen.
Unabhaengig davon sind ACQUIRE und RELEASE Einwegschranken und ordnen die
beiden Zugriffe nicht zueinander
(`Documentation/memory-barriers.txt:2009-2013` und `:2017-2021`).

**Herkunft, und das gehoert offen gesagt.** Der Fehler steckt in Lyudes
Skizze, nicht in der Umsetzung. Sein Wortlaut, Nachricht
`4ae8c1b945b83dfeafe4c89d59ec03c994242fd9.camel@redhat.com`:

> * Check the killed atomic to see if a kill event came in the window
>   before the fence was ready.
> * Set the atomic indicating that the fence is ready.

Erst pruefen, dann setzen. Der Diff ist seiner Skizze treu. Genau deshalb
kann die v4 nicht als "sein Entwurf plus eine Zeile" auftreten, ohne den
Tausch zu benennen.

**Wie schwer ist der Code wirklich.** Hier ist eine Einschraenkung faellig,
die keine der Vorlagen sauber hergeleitet hat. In der verlierenden
Verschraenkung steht `chan->killed` **auf 1**, denn `kill()` setzt es
unbedingt als erstes (`nouveau_chan.c:46`). Alle Verbraucher gattern darauf:
`nouveau_chan.c:59` und `:68`, `nouveau_exec.c:186` und `:379`,
`nouveau_gem.c:776`. Verloren geht nur `fctx->killed`
(`nouveau_fence.c:92`), dessen einziger Leser die Emit-Schranke
`nouveau_fence.c:230` ist. Folge ist kein Absturz, sondern dass Fences aus
den Kernpfaden, die `chan->killed` nicht pruefen (`nouveau_bo.c:969`,
`nouveau_dmem.c:267/517/809`, `dispnv04/crtc.c:1123`), noch in die
Pending-Liste eines toten Kanals wandern und erst nach dem 15-Sekunden-
Timeout aufgeben (`nouveau_fence.c:215`). Gegenueber dem heutigen Baum ist
das keine Verschlechterung, und gegenueber der v3-Fassung ist es besser,
denn dort blieb `chan->killed` auf 0.

**Warum es trotzdem ein Blocker ist.** Nicht wegen der Regressionsgefahr,
sondern weil der Patch das Gegenteil behauptet, `Cc: stable` traegt, an
dri-devel geht und unmittelbar auf den Satz "consider trying to write the
respin without using claude!" folgt. Ein falscher Ordnungsbeweis in genau
dieser Lage ist der teuerste Fehler, den diese Serie machen kann. Und die
Reparatur kostet zwei getauschte Zeilen.

**Was zu tun ist.** In `arm()`:

```c
	spin_lock_irqsave(&fctx->lock, flags);
	smp_store_release(&fctx->ready, true);
	/* Pairs with the smp_mb() in nouveau_channel_kill(). */
	smp_mb();
	killed = atomic_read(&chan->killed);
	spin_unlock_irqrestore(&fctx->lock, flags);

	if (killed)
		nouveau_fence_context_kill(fctx, -ENODEV);
```

und in `kill()` `smp_load_acquire(&fctx->ready)` statt `atomic_read()`. Die
Schranke in `arm()` ist nicht optional: der SB-Zyklus enthaelt zwei
Store-vor-Load-Kanten, jede braucht ihr eigenes `smp_mb()`, der kanonische
Test des Kernels setzt sie auf beide Prozesse
(`tools/memory-model/litmus-tests/SB+fencembonceonces.litmus:18-20` und
`:27-29`, Ergebnis `:4` "Never", ohne Schranken `SB+poonceonces.litmus:4`
"Sometimes"), und `Documentation/memory-barriers.txt:943` sagt, eine
Schranke ohne Gegenstueck sei fast sicher ein Fehler.

Dass `ready` **vor** der `killed`-Pruefung gesetzt wird, ist unbedenklich:
`arm()` laeuft erst nach erfolgreichem `context_new()`, der Kontext ist
vollstaendig.

### B5 HOCH: der Beweis im README hat drei umgekehrte Kanten

`README.md:53-58`. Im Einzelnen:

- `:54` "arm.ST(ready) -> kill.LD(ready), sonst haette kill die 1 gesehen".
  Wenn `kill` eine 0 las, laeuft die Kante genau andersherum,

erlaubt. Genau das bestaetigt die Durchzaehlung aus B1.

### B13 NIEDRIG, aber mit einer Korrektur: das gestrichene "(benign)" in 3/4

Vorschlaege: " (benign)" gehoert **nur** in die `nvkm_debug`-Zeichenkette.

perl checkpatch.pl --no-tree --strict --no-signoff only-debug.diff
  -> total: 0 errors, 1 warnings, 0 checks   (nur "Missing commit description")

Das ist zugleich semantisch richtig, denn die Fehlerzeile soll gerade nicht

## C) Commit-Text fuer 2/4

Voraussetzung: der Tausch aus B1 ist eingebaut und `ready` ist ein `bool`
mit `smp_store_release`/`smp_load_acquire`. Ohne den Tausch ist dieser Text
unwahr. Kein `Signed-off-by`, das setzt der Autor.

```
drm/nouveau: don't kill a half-initialised fence context

nouveau_channel_kill() dereferences chan->fence, but four of the six
fence backends publish that pointer before the object behind it can
be used:

	fctx = chan->fence = kzalloc_obj(*fctx);
	if (!fctx)
		return -ENOMEM;

	nouveau_fence_context_new(chan, &fctx->base);

and nouveau_fence_context_new() is what runs INIT_LIST_HEAD() on
fctx->pending and spin_lock_init() on fctx->lock.  A kill delivered
between the assignment and that call finds chan->fence non-NULL and
unusable: nouveau_fence_context_kill() takes a lock that was never
initialised and walks a list head that is still the NULL kzalloc()
left behind.  The NULL check in nouveau_channel_kill() does not cover
that.  nv04_fence_context_new() publishes last and has no window;
nv10, nv17, nv50 and nv84 do.

The window is not narrow.  The channel is schedulable, and its kill
event armed, long before the fence context exists: nouveau_channel_-
init() subscribes right after mapping userd, while the fence context
is only created at the very end of the same function.

Moving the subscription behind context_new() would only trade the
crash for a lost kill.  The channel is running either way, so a kill
arriving in the window would then be missed entirely, chan->killed
would stay 0, and nouveau_channel_idle() and the checks in
nouveau_gem_ioctl_pushbuf() and nouveau_exec_ioctl_exec() would go on
treating a dead channel as a live one.

Leave the subscription where it is and let the two sides hand over
instead.  Add fctx->ready, set by the new nouveau_fence_context_arm()
once the context is complete, and have each side store its own flag
before it loads the other's:

  nouveau_channel_kill():      store chan->killed, load fctx->ready
  nouveau_fence_context_arm(): store fctx->ready, load chan->killed

That is store buffering, so it needs a full barrier on both sides.
The flags are plain loads and stores and carry no ordering of their
own, and store-then-load is the one direction the CPU does not give
for free either.  With smp_mb() on each side this is exactly
tools/memory-model/litmus-tests/SB+fencembonceonces.litmus, whose
documented result is "Never": the two cannot miss each other, so the
kill is always delivered.  A barrier on only one side would have
nothing to pair with (Documentation/memory-barriers.txt).

Both sides seeing it is harmless.  nouveau_fence_context_kill() is
already called twice today, once from the kill path and once from
nouveau_fence_context_del(), and the second caller finds the pending
list empty.

fctx->ready is published with a store-release and read with a
load-acquire, so a killer that observes it also observes the
spin_lock_init() and INIT_LIST_HEAD() that precede it.  It is a plain
bool rather than an atomic_t: it is only ever set once and read, and
there is no read-modify-write anywhere.

fctx->lock is still held across the handover.  It gives no ordering,
one-way barriers do not relate the two accesses and the kill side
never takes it when it bails out, but it does delay an incoming kill
in nouveau_fence_context_kill() rather than blocking it.

The handover was suggested by Lyude Paul.  His sketch loaded
chan->killed before storing fctx->ready; the two are swapped here,
because with that order both sides can miss each other even under
sequential consistency, and no barrier placement can prevent it.

Fixes: ea13e5abf807 ("drm/nouveau: signal pending fences when channel has been killed")
Cc: stable@vger.kernel.org
Suggested-by: Lyude Paul <lyude@redhat.com>
Assisted-by: Claude:claude-opus-5
```

Zum Ton: die Zuschreibung steht vor der Abweichung, die Abweichung wird an
der Sache aufgehaengt und nicht an der Person, und sie wird benannt statt
verschwiegen. Verschwiegen faellt sie beim Lesen des Diffs auf, und dann ist
es schlimmer. Kein "but", kein "however", kein "his proposal misses".

Alternative Betreffzeilen, falls die Mechanik hinein soll:
`drm/nouveau: hand channel kills over to the fence context` oder
`drm/nouveau: fix kill of a partially initialised fence context`. Der alte
Betreff "subscribe to the channel-kill event after the fence context"
beschreibt eine Verschiebung, die es nicht mehr gibt.
