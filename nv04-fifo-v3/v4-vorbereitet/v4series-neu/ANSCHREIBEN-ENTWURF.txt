Withdrawn since v3

  v3 carried a patch that demoted one specific CACHE_ERROR to debug level
  and attributed it to a Mesa bind probe. I am withdrawing it, because that
  attribution does not survive a look at the tree. Method 0x0060 on this
  class is SET_CONTEXT_DMA_SEMAPHORE (nvhw/class/cl826f.h), and the only
  writers in tree are nv84_fence_emit32() and nv84_fence_sync32(), both on
  subchannel 0 (nvif/push006c.h). All 99 logged occurrences behind that
  patch read "subc 0 mthd 0060 data beef0201". The handle value is not from
  the kernel, it arrives with the channel allocation, but I have not
  established which userspace component picks it, and I have not
  established that those two writes are what faults. I will look at it
  separately rather than carry it here.

On 2/3, and the two places where it differs from the sketch

  The sketch checks chan->killed before setting ->ready, but each side has
  to store its own flag before loading the other's, or one interleaving
  loses the kill even under sequential consistency; swapped, with smp_mb()
  on both sides, it is the store-buffering pattern. And the kill side
  cannot take fctx->lock, because that lock is exactly what must not be
  touched before the context is built, so ->ready is a plain bool read
  outside the lock, published with release and read with acquire. The
  commit message has the full argument.

Testing

  Reference hardware: Apple Mac mini Late 2009, MCP79 / GeForce 9400M
  (NVAC), Core 2 Duo, Wayland (labwc).

  Build. Built against the stated base commit c21bb4193868. The nouveau
  module compiles and links with W=1 and no new warnings. checkpatch.pl
  --strict is clean on all three patches.

  Deliberate channel kills on Tesla, which is Lyude's question on 3/3.

  The kill path on this hardware has been exercised on purpose, not only
  observed, and under a real 3D workload. A local debug patch, which is not
  part of this series, synthesises a CACHE_ERROR on a nominated channel.
  The victim was SuperTuxKart, with its channel live under load. Verbatim,
  timestamps and unrelated lines elided:

    nouveau 0000:02:00.0: fifo: inject:   ch   2 [labwc[5670]] errored 0
    nouveau 0000:02:00.0: fifo: inject:   ch   3 [labwc[5670]] errored 0
    nouveau 0000:02:00.0: fifo: inject:   ch   4 [Xwayland[242990]] errored 0
    nouveau 0000:02:00.0: fifo: inject:   ch   5 [supertuxkart[1181685]] errored 0
    [...]
    nouveau 0000:02:00.0: fifo: ch 5 fault 1/3 in 10000ms window, skipping method and resuming (Tier-0)
    nouveau 0000:02:00.0: fifo: ch 5 fault 2/3 in 10000ms window, skipping method and resuming (Tier-0)
    nouveau 0000:02:00.0: fifo:000000:0005:0005:[supertuxkart[1181685]] errored - disabling channel
    nouveau 0000:02:00.0: Xwayland[242990]: channel 5 killed!
    supertuxkart[1181685]: segfault at 560800000000 ip 00007f617c0d5ba6 [...] in libgallium

  So on NVAC, with 3/3 in place, the ERRORED event is delivered, the handler
  runs, and the fence context is killed.

  One oddity in that output, orthogonal to this series but worth naming:
  the kill message says Xwayland while the nvkm side says supertuxkart for
  the same channel. The two names are separate snapshots of current->comm.
  nouveau_channel_init() builds the nvkm one when the channel is created
  (nouveau_chan.c), nouveau_drm_open() builds the DRM one when the file is
  opened (nouveau_drm.c), and nouveau_channel_killed() prints the latter.
  So they agree only when the same process did both. Why they diverge on
  four of the eight channel kills this machine has logged, the first on
  2026-07-25, I have not established.

  The compositor survived it. labwc kept the same pid across the kill and so
  did Xwayland, only the victim died, and the desktop stayed usable. That
  answer needed the watchdog out of the way first: this machine runs a local
  userspace service, no kernel code involved, that terminates the compositor
  when the kill message names one of the session's own processes, and lets
  greetd bring the session back. Because that message names the DRM client
  and not the process, as above, it would have fired on this kill too even
  though the victim was neither labwc nor Xwayland. So I stopped it for the
  test.

  Two limits on what that proves. The escalation that disabled the channel
  is local and not in this series; what this series contributes is that the
  event reaches a subscriber at all instead of being dropped into an empty
  notifier list. And the victim did not survive its own channel being
  killed: it segfaulted inside Mesa rather than handling the -ENODEV fences.
  Without the subscription it would have hung instead.

  Games and sustained 3D. glxgears without vsync for ten minutes, and
  SuperTuxKart for a full race, ten and a half minutes, both with 3/3 in
  place. In both runs everything the kernel said came at window creation
  and was the known benign gr DATA_ERROR trap: 71 of those for glxgears,
  three for SuperTuxKart, and none at all once either was running. No wedge,
  no unexpected kill, and the session came through both unchanged.

  Soak. Code equivalent to 1/3 and 3/3 has been running on this machine
  since 2026-07-25, across the kernel bumps 7.1.5 through 7.1.8, with no
  regression.
